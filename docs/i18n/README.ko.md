# agent-guardrails

AI 코딩 에이전트가 이미 완성된 코드를 건드리면 커밋을 거부하는 도구입니다.
파이썬 파일 두 개로 되어 있고, 설치할 의존성이 없습니다.

## 어떤 문제를 푸는가

AI 에이전트에게 코드를 맡기면, 문제는 대개 에이전트가 새로 쓴 코드에서 생기지
않습니다. 이미 잘 돌아가던 코드를 건드리면서 생깁니다.

예를 들어 "청구서 페이지 간격을 고쳐줘"라고 시키면, 에이전트가 바로 옆에 있는
세금 계산 코드까지 같이 정리해 놓는 일이 자주 있습니다. 에이전트가 부주의해서가
아닙니다. 그 코드가 왜 그렇게 생겼는지, 지금 모양이 되기까지 뭘 겪었는지 알 방법이
없기 때문입니다. 게다가 이런 변경은 리뷰에서 이상해 보이지 않습니다. 테스트도
없습니다. 잘 돌아가던 코드라서 아무도 테스트를 쓰지 않았기 때문입니다.

문서에 "이 파일은 건드리지 마세요"라고 적어두는 방법이 있습니다. 하지만 잘
지켜지지 않습니다. 실제로 겪은 일인데, 그 규칙은 반년 동안 문서에 있었고 계속
어겨졌습니다. 방금 그 문장을 읽은 에이전트도 어겼습니다. 아무 코드도 그 규칙을
검사하지 않았기 때문입니다.

이 도구는 그 규칙을 문서가 아니라 **실행되는 코드**로 만듭니다.

## 어떻게 동작하는가

먼저 `frozen.json`에 완성된 경로를 적습니다.

```json
{
  "frozen": [
    {
      "label": "결제",
      "paths": ["src/billing/charge.py"],
      "reason": "완성돼서 운영 중이고 로드맵에 없습니다.",
      "what_breaks": "계산이 틀려도 화면은 정상입니다. 금액만 달라집니다.",
      "before_you_touch": [
        "부분 환불은 여기가 아니라 refund.py가 담당합니다.",
        "실패하면 트랜잭션 전체를 되돌리는 설계입니다. 이걸 완화하지 마세요."
      ],
      "how_to_verify": "pytest tests/test_billing.py -q"
    }
  ]
}
```

그다음 pre-commit 훅을 설치하면, 이 경로를 고치는 커밋이 거부됩니다. 이때
터미널에 위에 적어둔 내용이 그대로 출력됩니다. 왜 잠갔는지, 틀리면 뭐가 깨지는지,
건드리기 전에 알아야 할 게 뭔지가 **막히는 그 순간에** 보입니다. 아무도 열어보지
않는 파일 안이 아니라요.

### 정말 고쳐야 한다면

커밋 메시지에 세 줄을 넣습니다.

```
UNFREEZE: src/billing/charge.py - 새 결제 수단 때문에 여기 분기가 필요합니다
UNFREEZE-IMPACT: 계산이 틀려도 화면은 정상이고 금액만 달라집니다
UNFREEZE-ROLLBACK: git revert <sha> 후 pytest tests/test_billing.py 재실행
```

세 줄 중 하나라도 빠지면 커밋이 거부됩니다.

왜 한 줄이 아니라 세 줄이냐면, 이유만 적으면 "왜 지금 고치는가"에만 답하기
때문입니다. 틀렸을 때 무슨 일이 생기는지, 어떻게 되돌리는지는 답하지 않습니다.
그런데 실제로 중요한 건 그 둘이고, 정확히 그 둘이 생략됩니다.

**영향과 복구를 못 쓰겠다면 아직 그 코드를 고칠 준비가 안 된 것입니다.** 그리고 그
사실을 프로덕션이 아니라 지금 알게 됩니다. 서류 작업을 시키려는 게 아니라, 이
판단이 세 줄을 쓰는 과정에서 저절로 나오게 하려는 것입니다.

## 무엇이 좋아지는가

**커밋을 전부 읽지 않아도 됩니다.** 밤사이 에이전트가 34개를 커밋했다고 합시다.
그중 두 개에만 UNFREEZE 줄이 붙어 있습니다. 그 둘을 먼저 보면 됩니다. 에이전트가
신중해진 게 아니라, 어디서 원래 범위를 벗어났는지 스스로 표시하게 된 것입니다.

**"간격 좀 고쳐줘"가 12개 파일로 돌아오지 않습니다.** 하나를 시켰는데 diff에 세금
계산 리팩터링과, 상류 API가 불안정해서 존재하는 재시도 루프의 "정리"까지 같이 들어
있는 상황이 줄어듭니다.

**뭔가를 받치고 있는 임시방편이 정리당하지 않습니다.** 어느 코드베이스에나 틀려
보이는데 실은 뭔가를 지탱하고 있는 줄이 있습니다. 몇 달에 한 번씩 누군가 그걸
정리하고, 나중에 정리 때문이라고는 아무도 생각하지 못하는 방식으로 문제가 생깁니다.
`before_you_touch`가 그 자리에 붙여둔 경고문 역할을 합니다.

**규칙이 누가 기억하느냐에 달려 있지 않게 됩니다.** "모바일 레이아웃 건드리지 마"는
조언이고, 통과되지 않는 커밋은 정보입니다. 후자는 새벽 3시에도, 당신을 처음 보는
모델에게도, 저장소에 들어온 첫 1분에도 작동합니다.

## 두 번째 도구

`check_git_policy.py`는 병합되지 않은 브랜치와 정리되지 않은 워크트리를 찾습니다.

브랜치가 남아 있는 것 자체는 큰 문제가 아닙니다. 문제는 **아직 반영되지 않은 진짜
작업이 거기 묻히는 것**입니다. 에이전트는 브랜치와 워크트리를 만들고 다음 작업으로
넘어가기 때문에 이런 게 계속 쌓입니다.

단순히 브랜치 목록을 출력하지는 않습니다. 패치 동등성(`git cherry`)으로 판정해서,
내용이 정말 main에 없는 브랜치와 squash나 rebase로 이미 반영된 브랜치를 구분합니다.
이 도구가 나온 프로젝트에서는 그 구분 덕분에 "미병합 브랜치 11개"가 "실제로 문제인
것 1개"로 줄었습니다.

## 어디서 나왔는가

AI 에이전트들이 몇 달 동안 프로덕션 코드를 만든 실제 프로젝트에서 나왔습니다. 그
과정에서 라이브가 60번 깨졌고, 그때마다 무슨 일이 있었는지와 다음부터 어떻게 할지를
기록했습니다. 그 규칙 중 코드로 만들 수 있는 것이 이 게이트가 됐습니다.

이 저장소에는 다른 프로젝트에도 적용되는 두 개와, 그 배경이 된 사건 28건을
실었습니다. 사건 기록은 `FAILURE_MODES.md`에 있습니다.

## 설치

```sh
git clone https://github.com/produckyou-design/agent-guardrails
./agent-guardrails/install.sh /path/to/your-repo
```

Windows:

```powershell
.\agent-guardrails\install.ps1 C:\path\to\your-repo
```

수동으로 하려면 `gates/*.py`를 프로젝트의 `scripts/`에 복사하고, `hooks/pre-commit`을
`.git/hooks/`에 넣고, `examples/workflow.yml`을 `.github/workflows/`로 복사하면 됩니다.

로컬 훅은 `--no-verify`로 건너뛸 수 있지만 CI는 건너뛸 수 없습니다. 둘 다 두는 것을
권합니다.

**처음에는 동결 목록을 비워두고 시작하세요.** 완성된 줄 알았던 파일을 에이전트가
고치는 날, 그 경로를 첫 항목으로 넣으면 됩니다.

## 전부 잠그면 안 됩니다

동결이 저장소 전체에 걸리면 게이트가 계속 울리게 되고, 그러면 진짜 위반도 같이
무시됩니다. 곧 작업할 예정인 경로는 열어두세요.

이 도구가 나온 프로젝트는 수백 개 경로 중 19개만 잠가두고 있습니다.

## 이 도구가 하지 않는 것

**성능이 얼마나 좋아지는지 측정하지 않습니다.** 이 README에 벤치마크 표가 없는 건
정직하게 만들 방법이 없기 때문입니다.

**시크릿이나 위험한 코드 패턴을 검사하지 않습니다.** gitleaks와 semgrep이 훨씬 잘
합니다. 이 도구는 그쪽에서 다루지 않는 문제를 다룹니다.

**에이전트가 더 좋은 코드를 쓰게 만들지 않습니다.** 잘못된 변경이 배포되기 전에
드러나게 할 뿐입니다.

**코드 리뷰를 대체하지 않습니다.** 리뷰가 가장 놓치기 쉬운 한 가지, 이미 맞게
돌아가던 코드에 대한 작고 그럴듯한 수정만 걸러냅니다.

## 테스트

```sh
python tests/test_gates.py
```

16개입니다. 임시 디렉터리에 실제 git 저장소를 만들고, 실제로 커밋을 하고, 게이트를
별도 프로세스로 실행합니다. 흉내(mock)를 쓰지 않은 이유는 검증하려는 대상이 게이트가
git을 어떻게 읽느냐이기 때문입니다.

비싸게 배운 버그도 테스트로 남겼습니다. 예를 들어 `src/db/sync-notices.py` 하나를
선언했는데 정규식이 하이픈을 잘라먹어서 `src/db/sync_orders.py`까지 조용히 풀리던
문제가 있었습니다.

검증이 실행되는 코드여야 한다고 주장하는 저장소라면 자기 것부터 증명할 수 있어야
합니다. 세 줄 규칙을 느슨하게 만들면 테스트 3개가 실패하고, 하이픈 처리를 망가뜨리면
경로 테스트가 실패합니다. 직접 해보셔도 됩니다.

## 같이 들어 있는 것

**`FAILURE_MODES.md`** — 이 게이트들이 나온 사건 28건입니다. 형식은 네 줄입니다.

```
증상  어떻게 보였나
원인  왜 그렇게 됐나
조치  무엇을 고쳤나
규칙  다음부터 어떻게 하나
```

무엇을 기록할지 판단하는 기준은 하나입니다. **"이걸 안 적으면 다음에 또 할까?"**
그렇다면 적습니다. 아무것도 안 깨졌더라도요. 반복되는 것은 대개 극적인 장애가 아니라
매번 똑같이 걸려 넘어지는 작은 것들입니다.

**`skill/SKILL.md`** — 에이전트가 읽는 운영 규칙입니다. 게이트는 기계적으로 검사할
수 있는 것만 잡습니다. 나머지, 예를 들어 실제로 돌린 검증만 돌렸다고 보고하는 것
같은 부분을 이 문서가 담당합니다.
