## AI エージェントについて誰も教えてくれないこと

エージェントがコードを下手に書いて本番を壊すことは、あまりありません。

壊すのは、すでに完成していたものに触ったときです。レビューでは完全に普通に見え、
テストもありません。そのコードは動いていたので、誰もテストを書こうと思わなかった
からです。

実際にはこう見えます。以下はすべて本番に出たものです。

**デプロイは成功した。画面は変わらなかった。**
CSS を直し、新しい HTML が出ました。ブラウザはキャッシュの古い CSS を使い続けま
した。パイプラインは緑、ログもきれい、サイトだけが間違っている。これが最悪の種類
です。成功シグナルが鳴ってしまうからです。

**push は成功した。デプロイは一度も走らなかった。**
コミットはある。GitHub にもある。デプロイのワークフローが手動だったので、何も
起きなかった。「上げた」と「出た」を二日間、同じものとして数えていました。

**本番で動いている機能のコードが、どのブランチにも無かった。**
消費側はデプロイされ、生成側はされていませんでした。画面はもう誰も書き込んでいない
ファイルを読み続け、最後に正常だったコピーを期限切れまで配っていました。

**その安全ルールは半年間ドキュメントにありました。**
「モバイルレイアウトには触らない」。書かれていて、合意もあり、すべてのエージェント
が読むルールファイルの中にありました。それを強制するものが何もありませんでした。
常に破られていました。その一文を読んだ直後のエージェントも含めて、全員が。

最後の一つが、このリポジトリが存在する理由のすべてです。

> 何にも読まれないルールは安全装置ではありません。安全装置に見えるメモです。

## これは何か

Python ファイル 2 つ。標準ライブラリだけです。モデルも API もサービスも、
インストールする依存もありません。

```
check_frozen.py       353 行   完成したコードをロックする
check_git_policy.py   223 行   埋もれた作業を見つける
```

AI エージェントが数か月にわたり本番コードを出し続け、60 回壊した実プロジェクトから
出てきました。壊れるたびに記録し、コードにできるものがこのゲートになりました。この
リポジトリには、他のプロジェクトにも当てはまる 2 つと、その背後にある 27 件を
収めています。

## 他を使わなくても、ここだけは持っていく価値があります

凍結は簡単です。難しいのは、どうやって解除するかです。「人に聞け」という答えは、
午前 3 時に働いているエージェントの前では持ちません。

うまくいくのはこれです。凍結されたパスに触るには、コミットメッセージに 3 行が必要
です。

```
UNFREEZE: src/billing/charge.py - 新しい決済手段のためにここに分岐がいる
UNFREEZE-IMPACT: 計算が誤っても画面は正常のまま、金額だけが変わる
UNFREEZE-ROLLBACK: git revert <sha> のあと pytest tests/test_billing.py を再実行
```

1 行でも欠ければコミットは拒否されます。

なぜ 1 行ではなく 3 行か。理由は「なぜ今か」にしか答えないからです。間違っていたら
何が起きるか、どうやって戻るかには答えません。その 2 つこそ午前 3 時に効いてくる
問いであり、まさにその 2 つが省略されます。

要点は書類仕事ではありません。**影響とロールバックが書けないなら、まだ解除できる
段階にいないということで、それを本番ではなく今、自分で見つけたということです。**
その判断は 3 行から勝手に出てきます。だから人に効くのと同じだけエージェントにも
効きます。

## 実際に何が良くなるか

**全部をレビューしなくてよくなります。**
一晩でエージェントが 34 件コミットしました。そのうち 2 件に UNFREEZE 行が付いて
います。まずその 2 件を読めばいい。ゲートがエージェントを慎重にしたのではありません。
**どこで道を外れたかを自分から言わせる**ようにしたのです。

**「余白を直して」が 12 ファイルの差分になって返ってこなくなります。**
1 つ頼んだのに、差分にはそれに加えて税額計算のリファクタと、上流 API が不安定だから
存在するリトライループの「整理」が入っています。エージェントが雑なのではありません。
**どの変なコードが理由があって変なのかを見分ける手段がないだけです。**
これからは、そのコードが触られた瞬間に自分でそう言います。

**何かを支えている応急処置が「改善」されなくなります。**
どのコードベースにも、間違って見えるのに何かを支えている行があります。四半期に一度
くらい誰かが整理し、整理と結び付けられない形で壊れます。`before_you_touch` はその柵に
打ち付けられた札で、誰も開かないファイルではなく端末に出ます。

**寝に行けます。**
エージェントが慎重になったからではありません。留守のあいだに起こりうる最悪が、
**起きているうちに自分で書いたリストで区切られているからです。**

**ルールが「誰かが覚えているか」に依存しなくなります。**
「モバイルレイアウトに触るな」は助言です。通らないコミットは情報です。違いは丁寧さ
ではありません。片方は午前 3 時に、あなたを知らないモデルに対して、リポジトリに来て
最初の 1 分から効きます。

## これがやらないこと

どれだけ良くなるかは測りません。この README にベンチマーク表がないのは、正直に
作る方法がないからです。でっち上げた表は 2 つのスクリプトより価値がありません。

秘密情報や危険なパターンの検査はしません。gitleaks と semgrep がここで作るどんな
ものより上手にやります。これはそちらがやらないことをやります。

エージェントに良いコードを書かせるものではありません。誤った変更が出る前に見える
ようにするものです。別々の問題であり、ここは後者だけを扱います。

レビューの代わりにはなりません。レビューが最も苦手とする種類、つまりすでに正しかった
ものへの、小さくもっともらしい隣接の編集を取り除くだけです。

## インストール

```sh
git clone https://github.com/produckyou-design/agent-guardrails
./agent-guardrails/install.sh /path/to/your-repo
```

Windows:

```powershell
.\agent-guardrails\install.ps1 C:\path\to\your-repo
```

または `gates/*.py` を `scripts/` にコピーし、pre-commit フックを入れ、
`.github/workflows/gates.yml` を追加します。ローカルフックは `--no-verify` で
飛ばせますが CI は飛ばせません。両方入れてください。

凍結リストは空から始めてください。完成したと思っていたものをエージェントが編集した
日に、最初のパスを追加すればいい。そう長くは待ちません。

## 持ちこたえる凍結エントリの書き方

理由のないパスは、次に必要になった人がそのまま解除します。凍結を持たせるのは
`what_breaks` です。解除する側が何を賭けているかを知る必要があるからです。

```json
{
  "label": "課金",
  "paths": ["src/billing/charge.py"],
  "reason": "完成して本番稼働中。どのロードマップにも無い。",
  "what_breaks": "計算が誤っても画面は正常に描画される。金額だけが変わる。",
  "before_you_touch": [
    "部分返金は refund.py の担当で、ここではない。",
    "失敗時はトランザクション全体を戻す設計。これを弱めない。"
  ],
  "how_to_verify": "pytest tests/test_billing.py -q"
}
```

`before_you_touch` は障害の行き先です。ここの各行は、高い授業料を払って学んだもので
あるべきです。

## 全部を凍結してはいけません

凍結がリポジトリ全体を覆うと、ゲートは狼少年になり、本物の違反もノイズと一緒に無視
されます。ロードマップがこれから触るパスは、開けたままにしてください。

元のプロジェクトは数百のうち 19 パスだけを凍結しています。

## テスト

```sh
python tests/test_gates.py
```

16 件です。一時ディレクトリに本物の git リポジトリを作り、本物のコミットをして、
ゲートをサブプロセスとして実行します。モックはありません。検証対象がゲートの
git の読み方そのものだからです。

高い授業料を払って学んだバグも入っています。`src/db/sync-notices.py` を宣言したら
正規表現がハイフンを飲み込み、`src/db/sync_orders.py` まで黙って解除されていた件など
です。

検証は実行されるコードであるべきだと主張するリポジトリなら、自分の分を証明できる
はずです。3 行ルールを緩めれば 3 件が落ち、ハイフン処理を壊せばパスのテストが落ちます。
試してみてください。

## 同梱物

`FAILURE_MODES.md` に、これらのゲートを生んだ事故が、役に立つ形式で入っています。

```
症状  どう見えたか
原因  なぜそうなったか
対処  何を変えたか
規則  今後どうするか
```

そのファイルに入れるかどうかの判断基準は 1 つです。**これを書かなければ、また同じ
ことをするか。** そうなら入れます。何も壊れていなくてもです。繰り返されるのは劇的な
障害ではほとんどありません。毎回踏み込んでしまう小さなループです。

`skill/SKILL.md` はエージェント側の半分で、ゲートと対になる運用ルールです。ゲートは
機械的に検査できるものを捕まえ、skill は残りを扱います。実際に走らせた検証について
正直に報告することなどです。
