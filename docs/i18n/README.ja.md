# agent-guardrails

AI コーディングエージェントがすでに完成したコードに手を入れたとき、コミットを
拒否するツールです。Python ファイル 2 つだけで、インストールする依存はありません。

## 何を解決するのか

AI エージェントにコードを任せたとき、問題はたいてい新しく書いたコードから起きません。
その途中で触ったコードから起きます。

たとえば「請求書ページの余白を直して」と頼んだとします。すぐ隣にある税額計算まで、
ついでに整理してしまうことがよくあります。これは不注意ではありません。エージェントには、
そのコードがなぜその形なのか、そこに至るまでに何があったのかを知る手段がないからです。
しかもこういう変更はレビューでも不自然に見えません。テストもありません。動いていた
コードなので、誰もテストを書こうと思わなかったからです。

プロジェクトのドキュメントに「このファイルは触るな」と書く方法はあります。それは
もちません。このツールが生まれたプロジェクトでは、その規則が半年間ドキュメントにあり、
ずっと破られ続けました。その一文を読んだ直後のエージェントも破りました。誰も、どの
コードもその規則を検査していなかったからです。

このツールは、その規則を**実際に実行されるもの**に変えます。

## どう動くのか

完成したパスを `frozen.json` に書きます。

```json
{
  "frozen": [
    {
      "label": "課金",
      "paths": ["src/billing/charge.py"],
      "reason": "完成して本番稼働中。どのロードマップにも入っていない。",
      "what_breaks": "計算が誤っても画面は正常に描画される。金額だけが変わる。",
      "before_you_touch": [
        "部分返金は refund.py の担当で、ここではない。",
        "失敗時はトランザクション全体を戻す設計。これを弱めないこと。"
      ],
      "how_to_verify": "pytest tests/test_billing.py -q"
    }
  ]
}
```

そのうえで pre-commit フックを入れると、これらのパスを編集したコミットは拒否されます。
そのとき、上に書いた内容がそのまま端末に出ます。なぜロックしたのか、間違えると何が
壊れるのか、触る前に何を知っておくべきなのか。**誰かが止められたその瞬間に**出ます。
誰も開かないファイルの中ではなく。

### どうしても変更が必要なら

コミットメッセージに 3 行入れます。

```
UNFREEZE: src/billing/charge.py - 新しい決済手段のためにここに分岐が必要
UNFREEZE-IMPACT: 計算が誤っても画面は正常のまま、金額だけが変わる
UNFREEZE-ROLLBACK: git revert <sha> のあと pytest tests/test_billing.py を再実行
```

3 行のうち 1 つでも欠ければ、コミットは拒否されます。

なぜ 1 行ではなく 3 行なのか。理由は「なぜ今変えるのか」にしか答えないからです。間違えた
ときに何が起きるか、どうやって元に戻るかには答えません。ところが実際に効いてくるのは
その 2 つで、まさにその 2 つが省かれます。

**影響とロールバックが書けないなら、そのコードを変える準備がまだできていません。** そして
それを本番ではなく今の時点で知ることになります。書類仕事をさせたいのではなく、この判断が
3 行を書く過程で自然に出てくるようにしたいのです。

## 何が良くなるのか

**すべてのコミットを読まなくてよくなります。** 一晩でエージェントが 34 件コミットしたと
します。そのうち 2 件に UNFREEZE 行が付いています。まずその 2 件を読めばいい。エージェントが
慎重になったのではなく、与えた範囲からどこで外れたかを自分で示すようになったのです。

**「余白を直して」が 12 ファイルの変更になって返ってこなくなります。** 1 つ頼んだのに、
差分には税額計算のリファクタと、上流 API が不安定だから存在するリトライループの「整理」まで
入っている。そういうことが減ります。

**何かを支えている応急処置が片付けられなくなります。** どのコードベースにも、間違って
見えるのに実は何かを支えている行があります。数か月に一度、誰かがそれを片付け、あとから
その片付けと結び付けられない形で何かが壊れます。`before_you_touch` はその場所に貼った
注意書きです。

**規則が「誰かが覚えているか」に左右されなくなります。** 「モバイルレイアウトに触るな」は
助言で、通らないコミットは情報です。後者は午前 3 時でも、あなたを見たことのないモデルにも、
リポジトリに来て最初の 1 分からでも効きます。

## 2 つ目のツール

`check_git_policy.py` は、マージされていないブランチと、チェックアウトしたまま放置された
worktree を見つけます。

ブランチが残っていること自体は大した問題ではありません。問題は**まだ反映されていない本物の
作業がそこに埋もれる**ことです。エージェントはブランチや worktree を作っては次の作業へ
進むので、これが溜まっていきます。

単にブランチを並べるだけではありません。パッチ等価性（`git cherry`）で判定し、内容が本当に
main にないブランチと、squash や rebase ですでに取り込まれたブランチを区別します。元の
プロジェクトでは、この区別によって「未マージ 11 本」が「本当に問題なのは 1 本」になりました。

## どこから来たか

AI エージェントが数か月にわたって本番コードを書いた実際のプロジェクトから来ています。その
過程で本番が 60 回壊れました。そのたびに何が起きたか、次はどうするかを書き残し、そのうち
コードにできる規則がこれらのゲートになりました。

このリポジトリには、そのプロジェクトの外でも通用する 2 つと、その背景にある 28 件を
収めています。記録は `FAILURE_MODES.md` にあります。

## インストール

```sh
git clone https://github.com/produckyou-design/agent-guardrails
./agent-guardrails/install.sh /path/to/your-repo
```

Windows:

```powershell
.\agent-guardrails\install.ps1 C:\path\to\your-repo
```

手動で入れるなら、`gates/*.py` をプロジェクトの `scripts/` にコピーし、`hooks/pre-commit` を
`.git/hooks/` に置き、`examples/workflow.yml` を `.github/workflows/` にコピーします。

ローカルフックは `--no-verify` で飛ばせますが、CI のジョブは飛ばせません。両方入れておく
価値があります。

**最初は凍結リストを空にして始めてください。** 完成したと思っていたファイルをエージェントが
編集した日に、そのパスを最初の 1 件として入れればいいです。

## 全部を凍結してはいけません

凍結がリポジトリ全体を覆うと、ゲートが鳴りっぱなしになり、本物の違反もノイズと一緒に無視
されます。これから作業するパスは開けておいてください。

元のプロジェクトは数百のうち 19 パスだけを凍結しています。

## このツールがやらないこと

**どれだけ良くなるかは測りません。** この README にベンチマーク表がないのは、正直に作る
方法がないからです。

**秘密情報や危険なコードパターンの検査はしません。** gitleaks と semgrep のほうがはるかに
得意です。このツールは、そちらが扱わない問題を扱います。

**エージェントに良いコードを書かせるものではありません。** 誤った変更が出荷される前に
見えるようにするだけです。

**コードレビューの代わりにはなりません。** レビューが最も見落としやすい 1 点、つまり
すでに正しかったコードへの小さくもっともらしい編集だけを取り除きます。

## テスト

```sh
python tests/test_gates.py
```

16 件あります。一時ディレクトリに実際の git リポジトリを作り、実際にコミットし、ゲートを
別プロセスとして実行します。モックは使っていません。検証したいのがゲートの git の読み方
そのものだからです。

高い授業料を払って学んだバグも入れてあります。たとえば `src/db/sync-notices.py` を宣言
すると、正規表現がハイフンを飲み込んで `src/db/sync_orders.py` まで黙って解除されていた、
という問題です。

検証は実行されるコードであるべきだと主張するリポジトリなら、まず自分の分を示せるはずです。
3 行ルールを緩めれば 3 件が落ち、ハイフンの扱いを壊せばパスのテストが落ちます。ご自分で
試してみてください。

## ほかに入っているもの

**`FAILURE_MODES.md`** には、これらのゲートが生まれた 28 件が入っています。1 件は 4 行です。

```
症状  どう見えたか
原因  なぜそうなったか
対処  何を変えたか
規則  今後どうするか
```

その file に入れるかどうかの判断基準は 1 つだけです。**これを書かなければ、また同じことを
するか。** 答えが「する」なら入れます。何も壊れていなくてもです。繰り返されるのは劇的な
障害ではめったになく、毎回同じところで足を取られる小さなことです。

**`skill/SKILL.md`** には、エージェントが読む運用ルールが入っています。ゲートは機械的に
検査できるものしか捕まえません。残りはこちらが引き受けます。たとえば、実際に走らせた検証
だけを報告することなどです。
